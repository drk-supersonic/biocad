# Roadmap to production

Честный список того, что осознанно оставлено как техдолг в этом MVP,
чего не хватает для боевого состояния, и в каком порядке это стоит закрывать.

## 1. Инфраструктура и деплой

- **Бесплатный план Render.** Backend задеплоен на `plan: free` — сервис
  засыпает после ~15 минут простоя и просыпается 30-50+ секунд на первый
  запрос. Для демонстрации это осознанный выбор (бюджет теста), для прода —
  первое, что нужно поменять: платный план с always-on, либо внешний
  keep-alive пинг как временная мера.
- **Один инстанс, без масштабирования.** Состояние плана хранится в памяти
  процесса (`app/state.py`), поэтому больше одного worker/инстанса
  backend поднять нельзя — второй инстанс не будет видеть изменения
  первого. Для прода нужно вынести состояние во внешнее хранилище
  (см. пункт 2), тогда снимается и это ограничение.

## 2. Хранение данных

- **Состояние только в памяти процесса.** Перезапуск backend (деплой,
  падение, засыпание/просыпание на free-плане Render иногда пересоздаёт
  процесс) — и весь план откатывается к сиду. Нет ни одной строчки
  персистентности. Для прода: минимум — SQLite/Postgres с одной таблицей
  задач, дальше можно наращивать (история изменений, версии плана).
- **Нет разделения по пользователям/проектам.** Одно глобальное состояние
  на весь backend — то есть все, кто открыл фронт, видят и правят один и
  тот же план одновременно, без какой-либо изоляции. Для реального
  использования нужны хотя бы project_id/сессии.

## 3. Надёжность и конкурентность

- **Нет блокировок на конкурентные правки.** Если два человека одновременно
  дёргают чат или REST-эндпоинты, возможны гонки при пересчёте расписания
  (scheduler.py). Для одного пользователя-демо это не проявляется, но это
  реальный риск при параллельном доступе.
- **Нет ретраев/таймаутов на вызовы OpenRouter.** Если LLM API отвечает
  медленно или падает — пользователь просто увидит ошибку в чате. Нужны
  таймаут с понятным сообщением и, возможно, один retry на transient-ошибки.

## 4. Безопасность

- **Никакой авторизации.** Любой, у кого есть ссылка на фронт, может
  смотреть и редактировать план (при условии, что впишет свой ключ
  OpenRouter). Для прода — минимум базовая аутентификация.
- **Ключ OpenRouter вводится пользователем в открытом виде на клиенте** и
  уходит в теле запроса на бэкенд при каждом сообщении чата. Это
  осознанное решение для тестового задания (чтобы не хранить чужой
  секрет на сервере), но для прода нормальный сценарий — свой серверный
  ключ с биллингом на организацию, а не ключ конечного пользователя.
- **Нет rate limiting на `/api/chat`.** Ничего не мешает заспамить чат и
  нагенерировать расходов на чужом OpenRouter-ключе (в рамках его же
  лимитов) или создать нагрузку на LLM. Нужен базовый rate limit по
  IP/сессии.

## 5. Тесты

- **Backend без единого автотеста.** Есть только smoke-тесты фронта
  (`frontend/src/__tests__`). Scheduler (пересчёт дат, каскадные сдвиги) и
  excel_io (парсинг/сборка) — как раз тот код, где легче всего словить
  регрессию незаметно; это первое, что стоит покрыть тестами.
- **Нет e2e-теста основного сценария** (загрузка → чат → экспорт).

## 6. UX / функциональность, оставленные вне MVP

- **Drag-n-drop по диаграмме отключён** (`isDisabled: true` в
  `GanttChart.jsx`) — правки идут только через чат, чтобы весь путь
  изменений проходил через LLM+MCP, как в ТЗ. Для прода логично включить
  и то, и другое: drag-n-drop с тем же вызовом MCP-инструментов под
  капотом, чтобы не разъезжались два пути изменений.
- **Нет истории изменений плана** (кто/когда что поменял) — ни в UI, ни в
  хранилище.
- **Нет отмены действия агента** ("отменить последнюю правку из чата").

## Порядок закрытия (если бы это уходило в прод)

1. Персистентность состояния (SQLite/Postgres) — без неё остальное бессмысленно.
2. Платный always-on план/инстанс — иначе прод с холодным стартом никто не примет.
3. Базовая аутентификация + свой серверный ключ LLM вместо пользовательского.
4. Тесты на scheduler и excel_io — самый большой риск тихой регрессии.
5. Rate limiting на чат, таймауты/ретраи на LLM.
6. Изоляция по проектам/пользователям, история изменений, drag-n-drop.
